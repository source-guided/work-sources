# Review the first completed result

Use this source for an independent workflow evaluation. The execution harness owns dispatch, preserved inputs, process isolation, report shape, and captured execution records. This source owns the review method; do not copy its product or UX criteria into executable prompts.

## Establish the expected outcome

Read preserved user input and clarifications through their references before reading the implementer's completion claims. Resolve the verification workflow through the current project reference and select the relevant domain sources. Derive checks from actual required outcomes and material decisions. Keep user requirements, workflow policies, assumptions, and new suggestions separate. A source read receipt is not evidence that its guidance was applied.

Inspect the first artifact without repairing it. Challenge the chosen decisions with relevant counterexamples, including unfamiliar or repeated work, supported nondefault scope, and transitions where the relevant domain source calls for them. Do not impose one UI pattern or add UI checks to a non-UI task. Distinguish an unsuitable decision, an implementation defect, missing input, and a verification claim unsupported by its evidence.

For each suspected contract violation, establish why the cited rule applies to this task and which product profile or restriction governs it. A generic format name does not automatically adopt every clause of a familiar specification. Classify conditional interpretations and unspecified resource limits explicitly rather than presenting them as confirmed defects. A disclosed implementation restriction remains a gap when it conflicts with an adopted requirement; disclosure alone is not acceptance. Explain observed impact and supported environment without inferring production frequency from a synthetic extreme.

## Tie observations to the exercised revision

Read the local report/execution contract supplied by the harness through a consumer reference. Use its execution capture tool for runtime observations and findings. The tool prepares a runtime copy, records the command, compares application file bytes and executable permissions before and after execution, and hashes the captured evidence. Keep test scripts and mutable outputs/state in the review workspace outside the runtime source tree. Declare additional screenshot or data evidence using a new output path for each execution; do not reuse a file from an earlier run. Record actual test inputs as directed by that contract.

If running the product requires changing its source or unsupported in-place generation, do not repair the first artifact or quietly bypass capture. Preserve the reason, separate any static inspection from executed behavior, and leave the affected runtime claim unverified. Dependency installation and interpreter identity are separate from application-source integrity; state material environment limits. Captured commands and hashes establish provenance, not that a test is meaningful or that a screenshot proves every interaction.

Use the contract's method distinction accurately: runtime for executed behavior, inspection for static observations, and scope for unverified or nonapplicable coverage. Do not label a runtime assertion as inspection merely to avoid missing execution evidence. For each finding retain reproduction, observed impact, its owning requirement or policy, and evidence that a reviewer can inspect. A guide's recommendation is not automatically a user requirement; explain applicability and limits.

## Report without rewriting history

Keep the first result and unsuccessful checks. Report observed behavior, findings, and unverified coverage separately. A successful process, a structurally valid report, and product acceptance are different outcomes. Do not convert counts into a quality score or claim universal compliance. Inspect the actual evidence and tool actions alongside trace audits; an omitted source access cannot be repaired retroactively by a later trace entry.

Distinguish a snapshot captured when the model process returned from an explicit later manual capture. A later manual snapshot does not establish what an earlier model result contained. Execution records are tool-owned by workflow convention inside the writable review workspace; inspect the actual tool use and do not present them as a separate trusted OS identity or tamper-proof attestation.

Subsequent source/workflow improvements are new revisions. Test them with a fresh task when transfer matters; do not provide the prior answer or evaluator findings to its implementer. Legitimate user clarifications remain part of the new run's input, with their source and scope. A fresh directory or an instruction not to read earlier artifacts is not a demonstrated read boundary. When claiming isolated or blind generation, use the execution harness to establish what inputs and tools are available and verify that prior artifacts, evaluation material and prior-session context cannot be accessed through those surfaces. Preserve that boundary evidence outside the implementer's environment. Report any remaining route of access or changed runtime condition rather than claiming stronger isolation than was established.

Apply it to the first artifact and the actual tool actions, not merely the implementer's completion claims. Keep the resulting findings separate from the preserved record of what the implementer originally knew and checked.
